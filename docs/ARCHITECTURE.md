## 1. 目标与边界

【已定】

- Alfred 是独立的新产品，不是 Robin 改名；从头设计，择取旧系统做得好的部分。
- 一个可自然对话的个人助手：安排日程、调查问题、减少重复工作，也能辅助开发。
- 随用户成长，不是每次都从零认识用户。
- 有全双工语音交互、语音汇报和"回来"的体验（例如"Bruce，欢迎回来"，并知道真实进展）。
- 屏幕上有一个一直在场、视觉统一稳定的形象，放大缩小都自然；不要脸和眼睛。
- 视觉参考 Bruce 的 portfolio 当前页面。
- 最终目标是做成**开源的 personal agent**。
- 先定架构，再动手。

【已定】（2026-11-17）

- 把 pi-web-robin 做成 **Mac 桌面 App**，并且把它**抽象出来**：Alfred 是一个 harness，Robin 现有的能力变成装在上面的模块。
- 在**本仓库**里做。
- **支持多设备**：同一个 Alfred，在 Mac、手机、别的电脑上都能用。
- 定位：围绕"和我的 agent 聊天"加"日常维护"的平台，每个人都能有一个自己的 AI 助手。

多设备指**一个用户、多台设备**，不是多用户。

【已定】（2026-11-22）

- Alfred 是给**任何人**装的开源 App，不是 Bruce 的私人工具。**任何功能都不能写死、不能只对一个人成立**：每个功能都要泛化成通用的能力。
- **能力由用户自己创建。** 用户（或经用户同意的 Alfred）不改代码就能新建、修改、删除自己的东西：领域、待办来源、自动任务和早报、技能、连接器、链接分区、笔记库、学习课题、提醒规则……App 自带的只是**可改、可删的默认值和样例**。
- 检验标准：一个陌生人装上，不改一行代码就能用，并且能把它改成他自己的。具体规则见第 9 节。

本草案不决定的事：第一版主打哪个场景、记忆保留规则、自我更新的权限级别。这些在第 12 节列为待定。

## 2. 一句话

**Alfred 的本体是一个常驻主节点上的"世界"（状态加事件）；每台设备都是它的一扇窗；语音模型、agent 引擎、连接器、业务模块都是插在它上面的可替换零件。**

世界负责记住、执行和决定何时开口。模型只负责听说和思考，换掉任何一个都不丢失用户的世界。换一台设备，看到的是同一个世界。

## 3. 总览

```text
┌──────────────────── 设备（都是客户端，地位平等）────────────────────┐
│  Mac App（Electron）    手机（PWA）    别的电脑（浏览器）   Telegram │
│  形象、主窗口、热键、    对话、待办、    同一套界面          渠道适配器│
│  在场感知、Mac 能力      推送、语音                                  │
└──────┬──────────────────┬──────────────────┬────────────────┬───────┘
       │ 本机              │ Tailscale / 局域网，配对后的设备令牌  │
       │                   │ 客户端协议（HTTP + SSE，公开、带版本）
┌──────▼───────────────────▼──────────────────▼────────────────▼───────┐
│  Alfred 主节点（Home node：launchd 常驻的 Node 进程，关窗口不停）      │
│  设备：配对、令牌、能力范围、设备能力的路由                            │
│  注意力：通知、投递时机、跨设备在场                                    │
│  世界：  事件日志、状态、记忆                                          │
│  任务：  可恢复的执行、权限、回执、调度                                │
│  模块：  待办、日程、简报……（业务规则 + 工具 + 视图）                  │
└───────┬───────────────────────────────────────┬──────────────────────┘
        │ 引擎接口                               │ 工具接口
┌───────▼─────────┐                    ┌────────▼──────────────────┐
│ Agent 引擎       │                    │ MCP 连接器（日历、邮件等） │
│ 先接 Pi，以后可换 │                    │ 设备能力（由某台设备提供）  │
└─────────────────┘                    └───────────────────────────┘
```

四层的归属：

| 层 | 是什么 | 谁拥有 |
|---|---|---|
| 设备 | 输入输出、呈现、本机能力 | Alfred，可以有多台 |
| 主节点 | 世界、任务、注意力、设备管理 | Alfred，只有一个 |
| 模块 | 一块业务：规则、工具、视图、定时 | Alfred 自带一批，个人模块另放 |
| 零件 | 语音模型、agent 引擎、连接器 | 第三方，通过接口替换 |

拓扑参考了 OpenClaw（常驻 Gateway 加多端节点，远程走 Tailscale）。区别在于：Alfred 以世界、回执、注意力和日常工作台为主，不以聊天渠道为主。

## 4. 核心概念

这些词在代码、协议和文档里只用一个意思。

| 概念 | 含义 | 不是什么 |
|---|---|---|
| 在场（Presence） | 用户此刻是否在、注意力在哪：离开、在但没互动、正在互动、正在通话 | 不是语音连接是否开着 |
| 对话（Conversation） | 围绕一个话题的线索，语音、文字、点击都往里写 | 不是一次语音连接，也不是引擎的会话 |
| 任务（Run） | 一次交给引擎的、可恢复的工作单元 | 不是引擎内部的子任务 |
| 操作与回执（Operation / Receipt） | 一次领域状态改动，以及它确实发生的证明 | 不是模型说"已完成" |
| 事件（Event） | 只追加的事实记录 | 不是日志文本 |
| 通知（Notice） | Alfred 想让用户知道的一件事，带投递状态 | 不是直接播出去的一句话 |
| 授权（Grant） | 对某类动作的许可，有范围和期限 | 不是引擎自己的工具白名单 |
| 能力档（Capability profile） | 一个任务可以用哪些工具、领域和目录，由代码决定 | 不由模型选择 |
| 主节点（Home node） | 唯一持有世界、执行任务的常驻进程 | 不是某个窗口，也不是 Mac App 本身 |
| 设备（Device） | 一台配对过的终端，有自己的令牌和能力范围 | 不是一个浏览器标签页，也不是一个用户 |
| 设备能力（Device capability） | 只有某台设备能做的事，例如 Mac 的系统通知、清理磁盘 | 不是主节点上的工具，设备离线时就不可用 |
| 模块（Module） | 一块业务：领域操作、agent 工具、事件类型、视图、定时任务 | 不是第三方插件，不做市场 |

## 5. 各部分

### 5.1 世界

**存储**：数据目录里一个 SQLite 文件。任何状态改动、它对应的事件、需要对外执行的待发记录，写在**同一个事务**里。Robin 的请求日志和任务库不在一个事务，中间有崩溃缺口，这里直接避开。

**事件日志**：只追加。界面上显示的、语音里说的，都能追溯到事件。"你离开后发生了什么"就是按时间查事件。

**领域模块**（待办、日程、调查、早报等）：只放业务规则。每个模块有两种适配器，调用的是同一组操作：

- 客户端命令（用户点击）。
- Agent 工具（引擎调用）。

**对外动作**用"待发 → 执行 → 回执"三步。结果不明的记为"不确定"，不可重入的动作绝不自动重试。这条规则来自 Robin。

**记忆**是数据目录里的三份 Markdown，用户可以直接打开和修改：

| 文件 | 内容 | 效力 | 谁能改 |
|---|---|---|---|
| `ASSISTANT.md` | 人设、语气 | 默认风格 | 只有用户 |
| `USER.md` | 用户偏好 | 当指令用 | Alfred 自动写，每次改动可见可撤销 |
| `MEMORY.md` | 事实和决定 | 只当事实，不当指令 | Alfred 自动写，每次改动可见可撤销 |

每次记忆写入都是一个事件。任何一份都不能授权跳过权限或改变安全规则。

**密钥**放系统钥匙串，不进数据库，不进仓库。

### 5.2 任务

状态机：

```text
queued → running ⇄ waiting_permission / waiting_input
            │
            ├→ completed
            ├→ failed
            └→ cancelling → cancelled

重启后：running 的任务变为 interrupted，等用户决定是否继续
```

规则：

- **不阻塞对话**：提交任务立刻返回，用户可以继续说话。新任务不取消旧任务。
- **打断不等于取消**：打断语音、静音、休眠、断线都不取消任务。只有明确的取消命令才取消。
- **取消要确认**：收到取消后进入 `cancelling`，以引擎的实际结果为准，不凭一句话就标成已取消。
- **租约和心跳**：执行者持有带期限的租约；旧执行者不能覆盖新执行者的结果。来自 Robin 的 `run-lease`。
- **重启不重跑**：重启后不自动重新执行，避免重复的对外动作。
- **成功以回执为准**：任务的结果里"做了什么"取自世界里的回执，不取自模型的陈述。
- **隔离**：引擎跑在子进程里，重的一轮不会卡住语音和界面。

**权限分四级**，策略在核心里，语音、点击、定时任务走同一套：

| 级别 | 例子 | 处理 |
|---|---|---|
| 只读 | 查日程、读邮件标题 | 不确认 |
| 本地可逆 | 加待办、改备注 | 直接做，回执带撤销 |
| 批量或计划 | 应用一天的安排 | 先预览，接受后执行 |
| 对外不可逆 | 发邮件、付款、永久删除 | 每次明确确认，授权只绑定这一次操作 |

- 权限检查在**领域操作里**，不在引擎里。所以换任何引擎，世界都能自己把关。
- **【已实现】提议**（2026-11-18）：任务可以把改动准备好，不马上做，留给用户在通知页决定，可以放好几天。
  - 接受时只执行预览过的那几步，只执行一次。
  - 期间它碰到的东西变了，就过期不执行。
  - 详见 `docs/design/workspace-architecture.md` 第 5.1 节和 W3。
- 引擎自带的工具（shell、改文件）由能力档加引擎的拦截点管。已核实（Pi 1.2.0 文档）：Pi 的扩展可以在工具调用前拦截并阻止，拦截器出错时默认阻止。
- 语音确认只转达用户**当轮明确说的**决定。模型不能自己造一个同意。
- 工具白名单不是系统沙箱，文档里要如实写明。

### 5.3 注意力

这是 Alfred 和同类项目差别最大的一层。**没有任何东西直接"说出来"**：任务结果、提醒、权限请求、欢迎，都先变成一条通知，再由这一层决定怎么送达。

通知的状态：`pending → claimed → presented → acknowledged`，或者 `expired`。

- **以呈现为送达**：客户端回报"开始播放"或"已显示"才算送达，模型生成了不算。
- **不重播**：开始播放后被打断，不再重播。多个客户端不会重复呈现同一条。
- **汇报不是指令**：通知的内容不能被当成用户指令去触发工具。

投递规则的起点（具体阈值待定）：

| 在场状态 | 普通通知 | 权限请求 |
|---|---|---|
| 离开 | 攒着，回来时合并成一次汇报 | 攒着，任务停在等待 |
| 在，但没互动 | 安静提示（形象上的标记），不出声 | 安静提示，可选出声 |
| 正在通话 | 等空档再说 | 等空档再说 |

空档的定义：用户没在说话、当前这一轮已经答完、没有音频在排队。

**欢迎回来**由真实事件驱动：离开超过一定时间后回来，触发一次，内容来自离开期间的事件。刷新页面或切换窗口不触发。

进度的规则：工具活动只更新形象和界面，不出声；阶段性进展最多隔一段时间说一次，而且只在安静时。

### 5.4 语音层

语音模型只当嘴和耳朵。接口与具体模型无关：

```ts
interface VoiceLayer {
  // 往上报
  onTranscript(speaker, text, startMs, endMs)
  onDelegation(id, recentTranscript)   // 前台请求后台干活
  onSpeakingChange(speaking)           // 驱动形象的状态
  onClosed(reason, usageSeconds)

  // 往下发
  deliver(route: 'context' | 'respond' | 'interrupt', text, delegationId?)
  instruct(text)
  mute(on); close()
}
```

- **音频路径**：客户端直连语音厂商。核心负责签发临时凭证或代做会话握手，长期密钥不到客户端。
- **前台模型可以直接调用一小组工具**：只读查询（今天的日程、现在几点）和本地可逆的改动（加一个待办）。这些调用走和别处相同的领域操作、权限检查和回执；回执返回后才说"好了"。
- **其余的事交给任务**：新建任务、补充任务、查状态、取消、转达权限决定。批量改动和对外不可逆的动作不能由前台直接做。前台不能选引擎怎么执行。
- **直接工具要少而简单**：语音模型调用工具的准确率有限（见调查第 3 节），所以只放单步、参数少、可撤销的动作。
- **两类模型，入口不同**：支持函数调用的模型（如 Higgs Realtime）直接调用上面这些工具。委派模式的模型（如 GPT-Live-1）自己不带工具，只发出一个不含文字的委派，连"加一个待办"这样的小事也要绕后台一圈；这时还要由核心根据近期转写判断它是新任务、补充、取消还是对权限的回答。
- **事实只从核心来**：前台不回答需要事实或推理的问题，交给后台。等结果时不猜。
- **没有新信息就不说话**；委派之前不先口头答应。
- **文字输入不经过前台模型**，直接成为对话里的一轮，进任务。语音、文字、点击共用同一份对话和事实。
- **连接按需建立**：热键或点击时连上，空闲后断开。在场感靠形象，不靠一直连着的语音会话。
- **隐私要如实说明**：被念出来的结果会经过语音厂商。不能只说"音频上云、资料不上云"。

**首选 Higgs Realtime**（Bruce 2026-11-14 的倾向）：它支持函数调用，说"加一个待办"时能直接调到工具；中文明确支持；按用量计费。

- 第二个适配器用来证明接口可换，选哪个待定（第 12 节第 12 条）。
- GPT-Live-1 排在后面：它自己不能调用工具，小事也要经过后台。
- Higgs Realtime Duplex 的 API 开放后再评估，它的工具调用方式目前没有文档。

各适配器的映射见 `docs/research/full-duplex-voice.md` 第 7 节。

### 5.5 Agent 引擎接口

Alfred 不自己写 agent 循环。引擎通过一个接口接入：

```ts
interface EnginePort {
  describe()                               // 身份和能力
  start(); health(); close()
  submit(run, context)                     // 执行一个任务，返回最终结果
  update(runId, input)                     // 给进行中的任务补充指令
  cancel(runId)
  respondPermission(runId, requestId, decision)
  respondInput(runId, requestId, answer)
  subscribe(listener)                      // 活动、权限请求、提问、结果
}
```

- **交给引擎的内容**：目标、对话的线索键、能力档、记忆上下文；会话里还没有的早期对话，只在第一次给一份。
- **不交给引擎的内容**：任务 id、归属、生命周期。这些留在核心。
- **第一个适配器是 Pi**，用它的 SDK 而不是命令行，跑在核心派生的工作子进程里。已核实（Pi 1.2.0 文档）：`createAgentSession()` 可直接建会话，`customTools` 可注入领域工具，`tool_call` 拦截点可接权限策略。
- **【已实现】每条对话一个持久的 Pi 会话**（2026-11-18）。会话存在 `<数据目录>/engine/sessions/<对话 id>/`，每个任务是其中一轮，模型能看到前几轮的工具结果，会话变长时由 Pi 压缩。任务的生命周期、租约、回执都不变。同一条对话的任务按顺序执行，所以不会两个进程同时写一个会话。
- **【已实现】会话保持热着，参照 Pi Web**（2026-11-18）：子进程在两轮之间保留每条对话的 Pi 会话和它的 MCP 连接，同一条对话的下一轮回到同一个子进程；那个子进程正忙着别的对话时，它先放掉这条对话的会话，再由另一个子进程从会话文件打开，所以任何时刻只有一个子进程持有一条对话。会话空闲 10 分钟后关闭；关闭时先发 `session_shutdown` 让 MCP 等扩展收尾，再 dispose。主节点退出时，子进程同样先关会话再退出。
- **【已实现】任务进行中可以插话**：你在一条对话的任务办到一半时说的话，送进正在进行的这一轮（Pi 的 `steer`），记成 `run.steered`；如果它恰好办完了，就作为下一句话。等你回答问题的任务不接受插话，只接受回答。
- **【已实现】每条对话可以选模型和思考强度**：存在对话上，不设就用 Pi 的默认；每轮结束记一条 `run.usage`（用的模型、思考强度、上下文占用）。模型列表来自 Pi 已登录的提供方。
- **【已实现】模型在工作子进程里运行**（`packages/engine-pi/src/pool.ts`）。工作进程按需启动、空闲 5 分钟后退出，任何一个都能接手任何对话，因为状态在会话文件里。Alfred 的工具仍在主节点里执行：工具调用经进程间通信回到主节点，在任务的租约下写世界，再把结果送回模型。子进程崩溃只让当前任务失败（`engine_crashed`），已做的改动保留在回执里，不会自动重做。
- **第二个适配器是 ACP**，接 Claude Code、Codex 等。这样开源用户不必用 Pi。

接口的形状参考了 Qwen Audio Agent 的 BackendPort，它已经用 ACP 接过包括 Pi 在内的多个引擎。

### 5.6 工具和连接器

- **领域工具**：对 Pi 直接注册为工具；对 ACP 引擎，通过一个本机 MCP 服务暴露同一组操作。
- **外部连接器**（日历、邮件等）：用现成的 MCP 服务，不自己写。
- **未知工具的分级**：先看 MCP 的工具标注（只读、破坏性等），用户可以覆盖；没有标注的默认按"需要确认"处理。
- **【已实现】通用工具交给 Pi，Alfred 把关**（2026-11-18）：
  - MCP 服务器写在 Alfred 自己的 `<数据目录>/mcp.json`，格式和 Pi、Claude Desktop 相同；不读用户个人的 Pi 配置。由 Pi 的 MCP、codemode、tool_search 扩展连接和调用，每轮结束时关闭连接。
  - 技能放在 `<数据目录>/skills/`。为了让模型能读技能，只开放 Pi 内置的 `read`；shell、写文件、编辑文件都不开放。
  - 模型子进程里有一个拦截扩展：服务器标注为只读的 MCP 工具、读技能目录里的文件，直接执行，只记一个步骤；其他调用（包括没有标注的 MCP 工具、读任何其他文件）都先经主节点问用户，一次只对这一次调用有效。允许并成功的、可能改动外部的调用记成回执 `external.called`。
  - 用户还不能覆盖某个工具的分级；需要时再加。

### 5.7 主节点、Mac App 和多设备

**一个大脑，多扇窗。** 世界只存在主节点上；设备不持有副本，不做双向同步（不用 CRDT）。设备可以缓存最近一次看到的内容，离线时只读，并如实显示"离线"；第一版离线时不接受写入。

**主节点**

- 一个 Node 进程，用 launchd 用户服务常驻。Mac App 第一次启动时安装并拉起它；关掉 App 窗口、退出 App，任务和定时都照常跑，手机也照常能连。
- 数据目录 `~/Library/Application Support/Zirma/`：一个 SQLite（世界、任务、通知、各模块的表）加三份记忆 Markdown。密钥放钥匙串。
- 【已实现】（2026-11-23）开发和生产不共用任何东西：数据目录、端口、launchd 代理、钥匙串服务名各一套，规则只在 `packages/core/src/stage.ts`。装好的 App 是生产，从源码跑的都是开发；开发运行碰到生产的数据或钥匙串就拒绝启动。打包只用已提交的代码。见 `docs/packaging.md` 第 4.1 节。
- 主节点自己托管界面的静态文件，所有设备打开的是同一套界面。
- 位置无关：以后可以搬到常开的 Mac mini 或服务器上，协议不变。那时 Mac App 远程连它，Mac 本机的能力变成"设备能力"（见下）。

**Mac App**

- Electron 外壳，加载主节点托管的界面。和 macOS 相关的东西都关在这一层：形象小窗（置顶、可缩小）、菜单栏、主窗口（Deck 和工作区）、全局热键、系统通知、麦克风权限、空闲/锁屏/唤醒上报、开机启动。
- 选 Electron 的理由：主节点和 Pi 本来就是 Node；麦克风、WebRTC、置顶窗口成熟；界面和手机浏览器一样跑在 Chromium 系，少一套渲染差异。Tauri 仍要带一个 Node 子进程；原生 Swift 体验最好，但界面要和手机各写一套。

**设备和配对**

- 新设备通过 Mac App 上的二维码配对，拿到一个设备令牌。设置里列出所有设备，可以随时吊销，吊销立即生效。
- 每台设备有类别（桌面、手机、浏览器）和能力范围。默认：手机能对话、看和改业务记录、接推送、用语音；不能开终端、不能浏览整块磁盘、不能动 Mac 本机能力。这延续了 Robin 里终端和 `/api/robin/mac` "只许本机"的规则，但改成按设备授权，而不是按是不是 localhost。
- 【已实现】（2026-11-23）每个地址谁能用，只写在一张表里：`packages/server/src/access.ts`。三级：`device`（任何配对的设备）、`dev`（用户放进开发会话的设备）、`local`（只有本机）。表里没有的地址对谁都是 404，本机也一样，所以新加的地址不会因为忘了写而对手机敞开。要先查数据才知道的（这个任务、文件、对话是不是开发会话的）留在 `http.ts` 用的地方，只会更严。
- 远程访问**默认关闭**。走 Tailscale：不开公网端口，并且自带 HTTPS。先用 Mac 上已装的 Tailscale Serve，之后换成主节点内嵌 tsnet（自己的名字 `alfred.<tailnet>.ts.net`），见 `docs/research/remote-access.md`。手机默认要装 Tailscale App；以后做原生 App 时内嵌 libtailscale。手机上的麦克风、Service Worker（PWA 安装和推送）都要求 HTTPS，局域网的 http 地址做不到。局域网加长密码作为备选。不提供直接暴露到公网的默认配置。

**设备能力**

- 设备连上主节点时登记自己能做的事（例如 Mac：系统通知、在 Finder 里显示、清理磁盘、截屏）。引擎通过主节点调用它们，主节点把调用路由到那台设备，权限检查照常在主节点做。
- 设备离线时，它的能力从可用工具里消失；不排队等它回来再执行对外动作。

**跨设备的在场和通知**

- 在场是用户的，不是设备的：主节点汇总各设备的上报（谁在前台、谁刚有输入、谁锁屏了），判断用户在哪台设备上。
- 通知只派给一个出口呈现（5.3 的 `claimed → presented`；派给谁由主节点决定，见 [注意力方案](design/attention.md)），其他设备只显示已读状态。Robin 已经遇到过这个需求："手机上看过的事，回到桌面不再说一遍"。
- 推送渠道：Mac 用系统通知；手机用 Web Push（Robin 已有实现）；Telegram 作为一个渠道适配器。渠道接受不等于用户看到。

**客户端协议**

- 命令走 HTTP POST，事件走 SSE（Server-Sent Events），带设备令牌和版本号。命令有请求 id 和响应，同一请求 id 重放返回原结果；事件有序、以 `seq` 为游标，断线重连时浏览器自带 `Last-Event-ID` 补发。用 SSE 而不是 WebSocket：事件只需要从主节点流向设备，SSE 不需要额外依赖，自带重连和续传，过 Tailscale 和代理也简单。语音音频不走这条路（5.4）。
- 所有设备地位平等，协议公开。Mac App 只是多了设备能力，不走私有通道。

### 5.8 Harness 和模块：怎么把 Robin 抽象出来

Robin 现在把 harness（会话、任务、通知、界面框架）和 Bruce 自己的业务（求职、外联、课程……）写在同一个 Next 应用里。Alfred 把这两者分开。

**Harness**（每个用户都有，本仓库公开）：

- 核心：世界、任务、注意力、定时、权限、记忆。
- 对话：对话线索、流式回复、工具调用的可视化、历史。
- 引擎接口和 Pi 适配器；MCP 连接器管理；技能文件。
- 主节点、客户端协议、设备配对、设备能力。
- 界面框架：形象、Deck、工作区、设置；Mac App。

**模块**（一块业务一个目录）。每个模块声明：

| 部分 | 内容 |
|---|---|
| 领域操作 | 业务规则；每个操作标明权限级别（5.2 的四级） |
| agent 工具 | 由领域操作适配，引擎和语音前台调用同一组操作 |
| 事件类型 | 写进世界的事件名和字段 |
| 视图 | 注册到工作区和 Deck 的界面 |
| 定时任务 | 例如早报的生成时间 |
| 设置 | 需要的凭证和选项；凭证进钥匙串 |
| 表和迁移 | 模块自己的表，和世界在同一个 SQLite，同一个事务里写事件 |

规则：

- 模块只通过 harness 提供的接口写世界（Robin 里的 `recordDomainEvent` 就是这个形状），不直接碰别的模块的表。
- 【已实现】（2026-11-23）模块的源码只从 `@alfred/module-kit` 拿核心的东西，不直接引用 `@alfred/core`。`module-kit` 开头列出了模块能用的那几样：世界和迁移、记自己的事件、领域、用户的语言、对外改动的队列、改自己提议的步骤。`packages/server/test/module-types.test.ts` 把这条规则锁住。
- 【已实现】（2026-11-23）设备能调的操作名列在每个模块的 `types.ts` 里（如 `TODO_OPS`），界面的 `api.op()` 只收这些名字；同一个测试核对这份清单和模块自己的操作一致。各模块快照的类型由界面的 `packages/ui/src/modules.ts` 统一给出（`snapshotOf`），页面不再自己强转。
- 用户亲手做的对外改动（例如邮件的星标）也走对外动作的队列：本地立刻改，外面那一步排队、重试、失败时告诉用户，和接受提议后的对外动作同一条路。
- 模块是一方代码，跟 Alfred 一起装，拥有完整的 Node 权限。文档里如实写明：装模块就是信任这段代码，不是沙箱。
- 第三方扩展仍然只走 MCP 和技能文件（第 8 节）。模块契约是内部接口，第一版不做模块市场。
- 公开仓库自带通用模块：待办、日程、笔记、链接、邮件摘要、早报。Bruce 自己的模块（求职、外联、课程、播客、AI 周报等）放私有仓库，按同一契约加载。

**Robin 的东西去哪里**

| Robin 现在 | Alfred 里 |
|---|---|
| `extension/robin/alfred-core/` | `packages/core`，整体搬。它本来就不依赖 Next、页面和 `store.ts`，只用到 `task-store.ts`、`paths.ts`、`dates.ts` |
| `extension/robin/*-domain.ts`、`*-tools.ts` | `modules/<名字>/`，按模块逐个搬业务规则和测试 |
| `app/api/robin/*` 的几十个路由 | 不逐个搬；统一成客户端协议上的模块命令 |
| `lib/rpc-manager.ts`、`session-reader.ts` | `packages/engines/pi`，取会话、流、取消的做法 |
| `ChatWindow`、`MessageView` | `packages/ui` 的对话视图，参考后重写 |
| Sky、`RobinLayer`、`ArrivalStage`、`HandOverStage` | `packages/ui` 的形象和注意力呈现 |
| Web Push、Telegram 桥 | 通知渠道适配器 |
| `/api/robin/mac`（只许本机） | Mac App 的设备能力 |
| 编程工作台（文件、终端、diff、worktree） | 第一版不搬（第 12 节第 13 条） |

**迁移方式：逐块替换，不一次切换。**

- Robin 在迁移期间照常每天用。一块业务搬到 Alfred 后，那块在 Robin 里停止写入。
- **一块业务同一时间只有一个写入方**。两个进程绝不同时写同一份数据。
- Robin 的数据（`~/.pi/robin`）由 Alfred 的导入命令按模块只读导入；不共用 Robin 的数据库文件。

## 6. 三条关键流程

**说一句话到结果回来**

1. 用户说话，语音模型判断需要干活，发出委派。
2. 客户端把委派和近期转写交给核心。核心建任务，立刻返回"已受理"。
3. 引擎在子进程里执行，调用领域工具。每次改动在世界里留下回执和事件。
4. 任务完成，核心生成一条通知。
5. 注意力层等到空档，让语音层说出结果，同时界面显示完整内容。客户端回报开始播放，通知标为已送达。

**说一句话，直接完成小事**

1. 用户说"加一个待办：周五交报告"。
2. 语音模型直接调用加待办的工具。
3. 核心执行领域操作，写回执和事件，把结果返回给语音模型。
4. 语音模型确认，界面上出现这条待办和撤销按钮。

**回来**

1. 桌面壳报告用户离开，注意力层开始攒通知。
2. 用户回来，桌面壳报告在场。
3. 注意力层查离开期间的事件和攒着的通知，合并成一次汇报。
4. 形象先醒来。是否出声、说多少，按用户的设置和投递规则决定。

**权限请求**

1. 引擎调用一个"对外不可逆"的领域操作。
2. 操作在世界这层被拦下，任务进入等待，生成一条权限通知。
3. 用户用语音或点击明确同意或拒绝。
4. 授权只绑定这一次操作。执行后写回执。

## 7. 安全和隐私

- 默认本机：数据、记忆、密钥都在主节点所在的机器上。
- 出本机的数据只有三类，都要在界面上说明：发给语音厂商的音频和被念出的结果、发给模型厂商的任务上下文、连接器访问的外部服务。
- 配对的设备看到的是同一份世界；远程访问开启后，这些内容经由用户自己的 Tailscale 网络或局域网到达设备。设备上只缓存最近看过的内容。
- 无遥测。
- 全程审计：每次操作、授权、记忆写入都有事件。
- 升级不能悄悄扩大权限。
- 不复制 Robin 的 `.env`、令牌、真实任务库到本仓库。

## 8. 成长和扩展

成长分三级，级别越高越需要用户明确同意：

| 级别 | 内容 | 方式 |
|---|---|---|
| 偏好 | 称呼、语气、默认做法 | 自动记到 `USER.md`，可见、可改、可撤销（2026-11-22 做成主节点的一张表，设置 → 通用 → 偏好，见 `docs/design/user-defined.md` 8.3） |
| 做事方法 | 可复用的步骤（技能文件） | Alfred 提议，用户批准后生效 |
| 新能力 | 新连接器、新代码 | 用户明确安装 |

扩展只用三样现成的东西：MCP（工具和连接器）、技能文件（做事方法）、接口适配器（语音和引擎）。第一版不发明插件系统。

## 9. 开源要求

- 仓库里没有任何个人数据、密钥、真实对话。
- 自带 key。没有任何 key 时，仍能以纯文字方式运行。
- 默认安全：不提供"全部自动批准"的默认配置；远程访问默认关闭，新设备必须在已有设备上确认配对。
- 公开仓库只带通用模块；任何人的个人模块都不进公开仓库。
- 客户端协议、引擎接口、语音接口都有契约测试，适配器的贡献者跑同一套测试。
- macOS 优先；跨平台时只需要改桌面壳。
- 许可证：MIT（仓库已有）。引入依赖前检查许可证，避开非商用条款。

### 9.1 不写死，能泛化，用户自己创建【已定】（2026-11-22）

- **个人的东西是数据，不是代码。** 名字、称呼、邮箱和账号、领域和分类、默认站点、提示词、时区、语言、作息、路径……都放在主节点的数据或设置里，代码里没有这些常量。代码里出现某个人的名字、账号或私人路径，就是 bug。
- **每个功能先问"别人怎么用"。** 从 Robin 搬过来的个人业务（求职、学习、研究……）先抽象成通用能力（例如学习模式的「课题」），某个人的具体内容只作为他的数据或私有模块。
- **用户能自己建。** 凡是列表、分类、规则、模板，都要有"新建 / 改 / 删"的入口，界面里能做，也能让 Alfred 代做（按第 8 节的同意级别）。内置项和用户建的项用同一套数据结构，内置项不享有特殊代码路径。
- **扩展走现成的口子**：技能文件、MCP 连接器、自动任务、模块（见第 8 节和 5.8 节）。新能力优先做成用户能装、能写的这几种东西，而不是改核心代码。
- **默认值要能换掉。** 默认值只是首次运行时写进用户数据的样例；删掉或改掉后，App 照常工作，升级也不会把它们写回来。
- **每篇设计文档写一节"用户能自己建什么、改什么"**，评审时按这一条检查。
- 产品本身的设计（形象、配色、版式）不算个人数据，可以内置；但主题、语言等仍可在设置里切换。

## 10. 仓库结构

```text
packages/
  protocol/    客户端协议的类型（只有类型，任何客户端都能引用）
  core/        世界、任务、注意力、提议、对外队列、自动任务、设备、项目（从 Robin 的 alfred-core 搬来）；引擎接口在这里
  module-kit/  模块契约：操作、查询、工具、视图、同步、投递；模块能用的核心接口也只从这里出
  server/      主节点：HTTP + SSE、访问表、设备配对和令牌、Google、推送、语音转写、开发会话（worktree、终端、进程）、托管界面
  engine-pi/   Pi 适配器：子进程池、模型账号、MCP 连接器、技能
  ui/          所有设备共用的界面：壳、各页、形象、设置（React + Vite）
  desktop/     Mac App：Electron 外壳、launchd 常驻主节点、热键、通知、在场上报、浏览器窗格、Mac 设备能力
modules/
  todo/ calendar/ mail/ links/   通用模块（早报是自动任务模板，不是模块）
prototype/     原型，保留作交互参考
scripts/       评测（eval）、语音对比（voice-bench）
docs/
```

还没有的（2026-11-23）：`voice/`（语音层，第 4 步）、`world-mcp/`（接 ACP 引擎时）、`modules/notes/`（方案已批准，见 `docs/design/notes.md`）。打包 Alfred.app 留到最后。

个人模块在另一个私有仓库，结构和 `modules/` 相同。

语言：TypeScript，Node 直接运行 `.ts`（只用可擦除的语法，服务端不需要构建步骤）。运行时：Node 24 以上（用内置的 `node:sqlite`）。存储：SQLite。界面：React + Vite 的单页应用，由主节点托管；不用 Next。理由：不需要服务端渲染；Robin 的审计里，编排散在 Next 进程、`after()` 和桥接脚本里，正是要避开的耦合。

## 11. 搭建顺序

每一步都是一条能跑通的竖切，有可观察的验收标准。

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 主节点和第一个模块，纯文字：搬 alfred-core；模块契约；待办模块（含从 Robin 导入）；Pi 适配器；客户端协议；最小界面（对话、待办、任务状态、通知） | 浏览器里一句指令 → 任务 → 一次待办改动 → 回执 → 显示；中途杀掉进程再启动，不重复执行；导入后的待办和 Robin 一致，Robin 侧停止写待办 |
| 2 | Mac App | 第一次打开即装好并拉起主节点；形象常驻；关掉窗口、退出 App，任务继续；锁屏回来只触发一次汇报；系统通知能点回对应的对话 |
| 3 | 多设备 | 手机扫码配对后能对话、改待办、收推送；同一条通知只在一台设备呈现；吊销后立即失效；手机调不到 Mac 本机能力；断线重连后事件不丢不重 |
| 4 | 语音和形象：先接 Higgs Realtime | 说"加一个待办"，前台直接调用工具，回执返回后才说完成；复杂请求变成任务，结果在空档说出；Mac 和手机都能通话 |
| 5 | 记忆、定时和更多模块：日程、邮件摘要、早报；个人模块按同一契约接入 | 偏好写入可见可撤销；早报按时生成并在回来时汇报；每搬完一个模块，Robin 里对应的那块停止写入 |

第 1 步就把模块契约定下来，因为后面每一步都要往上装东西。第 2、3 步把"桌面 App"和"多设备"放在语音之前：这两样是这次明确要的，而且它们决定主节点和协议的形状，语音只是又一个客户端。
