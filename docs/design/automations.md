## 0. 结论

1. 【事实】自动任务现在是「几点 + 星期几，到点把一段话交给 Zirma」。没人看着时只给只读和能撤销的工具，别的变成提议。这一层是对的，本文不动它。
2. 【事实】有三处在实际数据里已经出问题：没做成不会再试（早报连着 4 天失败，每天只试一次）；每期都接着同一个对话，上下文 5 天涨到 3.9 倍；只能按钟点触发，「有新邮件时」这类做不了。
3. 【建议】「什么时候」从一种变成三种：**按时间**（多四种写法）、**有事发生时**（模块自己声明能触发什么）、**按时间，但有新东西才跑**。到点只开一期、错过最多补一次、关掉就不触发，这三条规矩不变。
4. 【建议】没做成、而且什么都没改过的那一期，自动再试 3 次。改过东西的不再试，免得做两遍。
5. 【建议】每期从头开始，不带上一期的对话。要和上一期比的，只把上一期的结果给它。
6. 【建议】每条可以选自己的模型，页面上写这个月跑了几期、花了多少。页面改成侧栏列出每一条、右边是选中的那条。
7. 【建议】不做的：步骤图、cron 表达式、外面的 webhook、替你唤醒 Mac。理由在第 8 节。

## 1. 现状

【事实】

| | 现在 |
| --- | --- |
| 一条规则 | 名字、每次交给 Zirma 的话、几点、星期几、开关，加上结果怎么显示、通知里留几期、什么时候告诉你、颜色（`core_automations`） |
| 触发 | 主节点的钟每 30 秒看一次。任务的请求 id 是「规则 + 时间点」，重启、重复触发都只是重放 |
| 错过的 | 只补最近一个时间点，任务里会说晚了；晚了超过 12 小时就跳过，记 `automation.skipped` |
| 权限 | `automation` 档：不可逆的工具不给，不能问你，不能建或改自动任务，其余改动只能 `propose`。没人能点头的网址不打开（`web/tools.ts`） |
| 对话 | 一条规则一个对话，每期都进这个对话，引擎接着同一份历史（历史长了由 Pi 压缩） |
| 没做成 | 记成 `failed`，通知里多一条，不再试。做到一半主节点停了（比如 Mac 睡了），记成 `interrupted`，通知里问你要不要继续 |
| 模型 | 用你的默认模型。对话可以单独选模型，但自动任务的表单里没有这一项 |
| 花费 | 每期的 token 和费用记在 `run.usage` 事件里，页面上不显示 |
| 另外两套后台 | 模块的同步轮次（`passes.ts`，日历、邮件）和模块自己的后台任务（`ZirmaModule.jobs`：整理笔记、归类链接）。后一种也是没人看着的任务，但每一轮是一个新的对话，开关在各自的页面上，自动任务页上看不到 |

开发节点上早报的实际记录：

| 日期 | 结果 | 这一期结束时上下文的大小（token） | 这一期一共读进去的（输入 + 缓存读） |
| --- | --- | --- | --- |
| 11-19 | 完成 | 16,410 | 50,621 |
| 11-20 | 完成 | 30,530 | 79,635 |
| 11-21 | 完成 | 42,088 | 115,940 |
| 11-22 | 完成 | 51,582 | 92,871 |
| 11-23 | 完成 | 63,898 | 176,161 |

- 早报只需要今天的日历、待办和邮件，不需要前几天的对话。上下文每期多一万二左右，5 天涨到 3.9 倍；一期里模型要读好几轮，所以读进去的总量涨得更快。这 5 期还没长到触发压缩的程度。
- 那 4 期失败都没留下任何改动或提议，再试一次不会重复做任何事。每天只试了一次，通知里留下 4 条「没做成」。
- 失败的原因只记了一个代号（`engine_failed`），页面上看不出是没连上模型、key 被拒还是别的。

## 2. 什么时候

【建议】一条规则的「什么时候」是下面三种之一。表单里先选「按时间」或「有事发生时」。

### 2.1 按时间

| 写法 | 例子 | 存成 |
| --- | --- | --- |
| 每周 | 工作日 07:30；每天 09:00 和 17:00 | `{ at: ["09:00", "17:00"], days: [1…7] }`。就是现在的，`at` 可以有几个 |
| 每月 | 每月 1 号 09:00 | `{ at, dates: [1] }`。那个月没有这一天，就用月末 |
| 每隔 | 08:00 到 22:00 之间每 2 小时 | `{ everyHours: 2, from, to }`。最短 1 小时 |
| 一次 | 周五 15:00 | `{ on: "2026-12-04", at }`。跑完自己关掉，留在列表里 |

- 四种写法都只回答两个问题：现在之前最近的时间点是哪个（`latestSlot`），下一个是哪个（`nextSlot`）。触发、补跑、跳过的代码只认这两个函数，所以不用改。
- 已有的规则存的是 `{ at: "07:30", days }`，读的时候当成「每周」，不用迁移数据。
- 不让用户写 cron 表达式。对 Zirma 说「每月最后一个工作日」而四种写法表达不了时，它照实说做不到，并给出最接近的写法。
- **「一次」和提醒的分工**：「明天三点提醒我交表」是一条带钟点的待办，提醒已经会响（reminders.md）。「周五下午帮我查一下机票降了没有」才是一次性的自动任务。`automation_add` 的说明里写清这一条。

### 2.2 有事发生时

模块自己声明它能触发什么。核心和主节点不认识任何具体模块。

```ts
// module-kit：ZirmaModule.triggers
interface ModuleTrigger {
  label: Record<Locale, string>;      // 表单里显示的：「有新邮件时」
  events: readonly string[];          // 哪些事件之后来问一次
  /** 从上次到现在有什么。没有就返回 null。不调模型。 */
  collect(world: World, since: { seq: number; at: string }): { upTo: number; about: string } | null;
}
```

- **流程**：主节点听事件（已有的 `onEvents`）。某条规则的触发器点名的事件来了，就调它的 `collect`。有东西就开一期，没有就什么都不做。
- **只开一期**：请求 id 是「规则 + `upTo`」，和按时间的一样，重放不会开第二期。规则里记着上次看到哪（现在的 `last_slot` 旁边加一个游标）。
- **告诉这一期的话**：规则自己的那段话，后面加上 `about`，比如「（新到 3 封邮件，id：…）」。`about` 里只放 id 和数量，不放别人写的字；内容由这一期自己用工具去读，读到的照旧当成材料，不当成指令。
- **打开的时候**：游标从现在算起，以前的不补。主节点关了几天再开，攒下的算一批，只开一期。
- **不会自己触发自己**：Zirma 的任务写下的事件（`actor` 是 `alfred`）不触发任何自动任务。只有你做的事和同步读到的事算数。
- **第一版只带一个触发器**：邮件模块的「有新邮件时」。「新」的算法和提醒里的一样：没读过、在游标之后收到的。别的（收下链接时、日程有变化时）等有了具体用处再由模块加，私有模块也用同一个接口。

### 2.3 按时间，但有新东西才跑

按时间的规则可以再挂一个条件：「有……才跑」，选项就是 2.2 里模块声明的那些触发器。

- 到点时先调 `collect`。返回 null 就不开这一期，记一条 `automation.skipped`（原因 `nothing_new`），不调模型，不进通知。页面的记录里写「09:00 没有新邮件，没跑」。
- 这和现在的「有改动或提议时才告诉你」不一样：那个选项照样跑一遍、照样花一次调用，只是不说。
- 样例「从邮件里挑待办」正好用得上：改成「每天 09:00，有新邮件才跑」，要看哪几封由 `about` 给，不用再靠「最近两天」去猜。

### 2.4 限制

- **每条每天最多 24 期**（「每隔」和「有事发生时」的规则；可以在「更多」里改）。到了上限就跳过，记 `automation.skipped`（原因 `daily_cap`），页面上写一行，不进通知。
- **同一条规则同一时间只有一期在跑**。上一期没跑完，新来的事等着，下一次 `collect` 会一起带上。
- 「有事发生时」的规则，「什么时候告诉你」默认是「有改动或提议时」，免得一天进来二十条通知。

## 3. 没做成怎么办

【建议】

- **再试的条件**：这一期以 `failed` 或 `interrupted` 结束，并且没留下任何东西：没有改动、没有提议、没有对外的调用。判断方法是这一期名下除了 `run.*` 以外没有别的事件，`result-delivery.ts` 判断「有没有改动」用的就是这一条。
- **怎么试**：2 分钟后、10 分钟后、30 分钟后，最多 3 次。每次是一个新任务（请求 id 是「规则 + 时间点 + 第几次」）。下一个时间点到了、规则被关了或改了，就不再试。
- **再试期间不进通知**。页面那一行写「没做成，07:32 再试」。3 次都没成，通知里只进一条。
- **留下了东西的不再试**：再跑一遍可能把同一件事做两遍。通知里照旧说没做成，并列出它已经做了什么。
- **做到一半主节点停了的**：没留下东西的，按上面的规矩自动再试，不再问你要不要继续。留下了东西的，和现在一样问你。
- **连着 3 期都没做成**：通知里说一次「早报连着 3 期没做成」，带上原因。之后再失败不再加通知，直到有一期做成。规则不会被自动关掉，关不关由你定。
- **原因用人话说**：没有可用的模型、key 被拒、额度用完、连不上网。现在任务的结果里只有一个代号，引擎能不能给出这几种区分，做的时候先查。【待查】

## 4. 每期从头开始

【建议】

- 每期一个新的上下文，不接上一期的对话。第 1 节的数字是理由：早报不需要昨天的对话，上下文却每期多一万二左右，而且上一期写错的东西会留在历史里影响下一期。
- **要和上一期比的**（「和昨天比有什么变化」）：每条规则一个选项「接着上一期」，默认关。打开以后，把上一期做成的那次结果原文放在这一期的话后面，最多 4000 字（任务结果本来就按这个长度存）。给的是结果，不是整段对话。
- **按日期回查不变**：自动任务页的运行历史是按规则查任务的（`core_runs.automation_id`），不靠同一个对话。
- **你在某一期后面追问**：接的是那一期的上下文，不影响下一期。
- **实现有两条路**，做的时候定：每期一个新对话（模块的后台任务就是这么做的），或者留着一个对话、每期换一个引擎会话。后一条页面改得少，但 `run-sources.ts` 是按对话找会话文件的，要一起改。

## 5. 模型和花费

【建议】

- 规则多两项：`model` 和 `thinking`，空着就用你的默认。表单的「更多」里用对话那个模型选择器。巡查类的规则可以配一个便宜的模型，早报可以配一个好的。
- 页面上每条写一行：「这个月 26 期，约 $0.41」。数字从 `run.usage` 事件按规则加起来。用订阅的模型没有费用，只写期数和 token 数。
- 第一版不做金额上限。第 2.4 节的每天期数上限已经封住了最坏的情况。

【建议】按 workspace-architecture.md「页面自己的侧栏」那条规矩，自动任务是下一个：侧栏列出每一条，右边是选中的那条。


- **「最近」把每一期都列出来**，包括没跑的：跳过（为什么）、没有新东西、到了每天上限、再试中。这些现在只在事件里，页面上看不到。
- **「Zirma 自己在做的」**：模块的后台任务（整理笔记、归类链接）也列在这里，写着开没开、上一轮什么时候、这个月花了多少。点它去那个功能自己的页面，开关仍然只在那里（links-autofile.md 定的：开关只有一处）。这样没人看着时会跑的东西，在一个地方都看得到。这一块要等 module-host.md 的 `jobs[*].due` 定下来，放在最后做。
- 侧栏收起、手机上，列表放回页面里，和笔记、链接、邮件的做法一样。
- 文字照 style.md：状态一行说完，不写句子。中英文、窄宽度都不能叠字。

## 7. 试一次

【建议】表单里多一个「试一次」：

- 用只读的工具跑一遍（连能撤销的改动和提议也不给），结果显示在表单下面。
- 不进通知，不算进运行历史，不动「上次」和时间表。
- 用处是打开之前先看它会交出什么。「现在跑一次」仍然是真跑。

## 8. 不做的

- **不做步骤图**。Zapier、n8n 那种「触发 → 步骤 → 步骤」每一步都固定，适合接系统。Zirma 的规则是一段话，怎么做由模型当场决定，改一条规则就是改一句话。可查这一点由运行记录、来源回溯和提议来保证。
- **不让用户写 cron 表达式**。四种写法够用，其余的对 Zirma 说。
- **不接外面的 webhook**。要给主节点开一个对外的入口，等远程访问那条线定了再说。
- **不替你唤醒 Mac**。定时唤醒要管理员权限，合着盖时也不可靠。Mac 睡着时错过的，醒来 12 小时内补一次并说明晚了，这条规矩留着。
- **不单独处理时区**。时间按主节点这台机器的时钟。带着笔记本出差，系统时区变了，规则就跟着走；主节点留在家里，就按家里的时间。
- **连着失败不自动关掉规则**（第 3 节）。
- **MCP 连接器不能当触发器**。它们不会主动推事件，要盯着连接器里的东西，用「每隔」加一段话。
