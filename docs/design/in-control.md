# 人始终在控制：产品、地图、决策（草案）

> 状态：v0.3（2026-11-24），**待看，未批准**。代码没开始。

> 原型：`prototype/in-control.html`（四页：会话、产品、地图、决策；中英文、浅深色、手机宽度；样例项目是一个虚构的作品集网站）。

## 0. 结论

1. **人控制的是决定，不是代码。**【已定】不是自己写的代码，看 diff 也看不出改了什么。代码归 agent，决定归人。
2. **一个项目长期只跟三样东西**【已定】：
   - **产品**：我想要什么。开题和产品细节放在一起，都是你对这个产品的想象。
   - **地图**：代码现在分哪几块，每块提供什么，健不健康。哪里出了问题，从那一块开始查。
   - **决策**：为什么是现在这样。全项目共用一棵树，哪里没对齐就回到那里。
3. **会话是干活的地方**【已定】：进度行原地更新，碰到底线停下来问，做完一张回执。
4. **三样东西互相连着。** 一张功能卡能看到实现它的模块和经过的决定；一个模块能看到它服务的功能和最近的决定。跟住项目靠查得到，不靠记性。
5. **产品是看得见、能直接改的计划**【已定】，不是一问一答的 grill me。没想清的地方标成卡上的空格，你在卡上选。
6. **地图要让人知道怎么改进**【已定】：结构和健康由机器从代码算，技术债变成最多三张改进卡，点一张就是一个任务。
7. **不能不择手段。**【已定】产品里写的"不用什么"加自带原则就是底线，每一轮由机器查。
8. **注意力最贵。** 平时只有会话；产品、地图、决策是你想看时才去看的地方，没事不打扰。

## 1. 问题

- **失控**：agent 写了很多，人说不清项目现在什么样、为什么是这样、哪一步开始和自己想的不一样。
- **只会对话的工具会积累技术债**【已定】：时间一长，代码越来越乱，人也不知道从哪改起。
- **diff 不是答案**【已定】，**更多的确认也不是答案**（人会不看就点）。
- **只和 agent 来回问答，计划看不见**【已定】：问完了，你脑子里没有一张图，过几天也找不回来。
- **agent 会为了达到目的走捷径**【已定】：加一个不必要的依赖、多装一个 Python、关掉一个测试。

## 2. 通用语言

| 词 | 是什么 | 不是什么 |
|---|---|---|
| 产品 | 项目的一页：给谁、花多大力气、不用什么，加上按地方排开的功能卡 | 不是需求文档，不是聊天记录 |
| 地方 | 用户碰得到的东西：页面、流程、命令【已定】 | 不是模块 |
| 功能卡 | 产品里的一件事，挂在一个地方下面；状态：想法、定了、在做、做好、有问题 | 不是任务（一张卡可以做好几次） |
| 空格 | 卡上没想清的一处，带几个选项和各自的后果 | 不是一个提问 |
| 地图 | 代码分成的几大块（模块），它们谁用谁，每块健不健康 | 不是文件树，不是 UML |
| 模块 | 代码里的一块，用"它提供什么"起名，例如"存作品""把作品变成网页" | 不是一个文件或文件夹（底下对应一组路径） |
| 健康 | 机器从代码算出来的信号：测试、大小、越界、依赖、没人用、改得勤 | 不是 agent 的感觉 |
| 改进卡 | 地图给出的一条可以做的改进：改什么、为什么、多大、风险 | 不是待办清单（最多三张） |
| 决定 | 有不止一条路、而且结果或代价明显不同的选择：问题、选项和后果、选了哪个、谁定的 | 不是每一步操作 |
| 决策树 | 全项目的决定：主线是已接受的，支线是会话里还没接受或放弃的；依赖连着 | 不是按任务的树 |
| 快照 | 决定做出那一刻的代码状态（一个提交） | 用户看不到它，只看到「回到这里」 |
| 范围 | 这次会话能动哪些模块，由你从哪里开始决定 | 不是权限模式 |
| 底线 | 项目不许做的事：产品里的"不用什么"，加自带原则 | 不靠 agent 自觉，机器查 |
| 回执 | 会话做完的一张卡：效果、决定、底线、没验证 | 不是文件列表 |

## 3. 一个项目：三样东西加会话

| | 回答 | 谁维护 | 你什么时候看 |
|---|---|---|---|
| 产品 | 我想要什么 | 你和 Zirma 一起，在这一页上改 | 想功能、开新东西时 |
| 地图 | 代码现在什么样 | 结构和健康由机器算；每块一句话说明 Zirma 写、你确认 | 出问题时，或它提示有改进时 |
| 决策 | 为什么是这样 | 会话里自动记下 | 觉得不对劲时 |
| 会话 | 正在做什么 | Zirma 做，你看回执 | 每天 |

**连法**：

- 功能卡 → 实现它的模块、为它做的决定。
- 模块 → 它服务的功能卡、最近的决定、它的健康。
- 决定 → 它为哪张卡做的、碰了哪些模块、依赖它的后续决定。
- 会话 → 从一张卡或一个模块开始；做完时卡的状态、地图、决策树都跟着变，回执里各一句。

**两项交叉检查**（机器做，结果进地图的改进卡）：

- 标了"做好"的卡，没有模块实现它：可能没做完。
- 没有任何卡、也没有别的模块用到的模块：可能是死代码。

## 4. 产品

【已定】开题和产品细节放在一起，都是你对这个产品的想象；计划要可视化、能自己浏览。

### 4.1 布局

- **顶上一条**：给谁、花多大力气（"一个周末能上线"或"要长期用"）、不用什么、用什么做（这一条连到决策树上的那个决定）。
- **下面按地方排开**：横向是用户走过的地方（首页 → 作品详情 → 关于 → 联系），每个地方下面竖着挂功能卡。规划了还没有的地方画成虚线。
- **存的东西单独一行**：作品、留言。
- **卡的状态**：想法（虚线）、定了、在做（连到那个会话）、做好、有问题（连到地图上出问题的那块）。
- 参考 Jeff Patton 的用户故事地图：横向是用户的路径，纵向是功能的先后。

### 4.2 和 Zirma 一起想：空格，不是问答

- 页面底下一行输入框「和 Zirma 一起想」。你说"作品区加个按年份筛选"，它**在页面上原地加一张卡**，对话里只回一句（`alfred-less-talk-input`）。
- 它没把握的地方不追问，**标成卡上的空格**：一个问题、两三个选项、每个的后果，先填上它的猜测（`alfred-guess-dont-ask`）。你在卡上点就行，不想管就用它猜的。
- 空格碰到底线时直接说明：例如"约稿表单的留言存哪"，"加一个后端"那个选项写着「越过了：不要后端」。
- 一张卡的空格都定了，状态从"想法"变成"定了"，卡上出现「做这个」。

### 4.3 开题就是第一版产品

- 空项目时，你说一句"我想做一个放我画作的个人网站"，Zirma **先猜一整版**：顶上一条和几个地方、几张卡，全部是"想法"。
- 你点掉不对的、改掉，点「就这样开始」：这一版成了决策树的根，"不用什么"成了底线。
- 以后改顶上一条（比如力气从"一个周末"改成"要长期用"），决策树上受影响的决定会标出来。
- 参考 Shape Up 的 pitch（appetite、no-gos）和 Spec Kit 的 constitution。

### 4.4 怎么不变成没人更新的文档

- **会话从卡开始**：「做这个」开一个会话，做完卡自动变"做好"，并连上它用到的模块和决定。
- **改一张做好的卡就生成一个任务**，开始前列出会碰到的模块。
- **直接在会话里提的新东西**，回执里问一句"要不要在产品里加一张卡"，默认加在它最像的那个地方下面。

## 5. 地图

【已定】地图跟的是整个系统架构：代码有哪几大块、各干什么，抽象成一个个模块、一个个功能提供者；哪里有问题，直接从那一块开始查。

### 5.1 分块

- 顶层 5 到 12 块，用"它提供什么"起名：存作品、把作品变成网页、压图片、样子、上线、收消息。
- 点开一块看里面更小的部分（同样的样子，下一层）。
- 块和块之间的箭头是"用到"，由代码里的引用关系算出来。
- 产品里定了、代码里还没有的模块（例如"收消息"），画成虚线。
- 第一次（或者代码分得很乱、算不出块）时，Zirma 按文件夹和引用关系提一个分块方案，你点头才用。之后新代码落在哪块由路径决定；落不进任何一块的，回执里提一句。
- 参考 C4 模型的第二、三级；Backstage 软件目录（每个组件一句说明、谁用它）。

### 5.2 每一块显示什么

- **一句话职责**：Zirma 写，你确认。代码和说明对不上时（例如"作品内容"里出现了关于页的文字），标成「可能过时」，点一下让它重写。
- **提供什么**：几条能力，用人话。
- **用到谁、谁用它**。
- **服务的功能卡**（连到产品）。
- **健康**（第 5.3 节）。
- **最近的决定**（连到决策树）。
- **在哪**：对应的文件夹，默认折叠，想看能看。
- 两个按钮：「从这里查」（出问题时，开一个范围是这块的会话，先带上这块的说明、健康和最近的决定）和「改进它」（有改进卡时）。

### 5.3 健康：机器算，不靠感觉

每次会话结束、接受时，主节点重算一次，都是确定的计算：

- **测试**：有几个测试管这块，最近一次过没过。
- **大小**：行数，和一个月前比。
- **越界**：别的块直接用了它内部的文件，没有经过它提供的东西。
- **依赖**：它用了哪些外部包，有没有过期或已知漏洞。
- **没人用**：没有功能卡、也没有别的块用到它。
- **改得勤**：最近改得多，测试却少（Adam Tornhill 说的热点：改得勤又没人管的地方最容易出事）。

每块只显示一个颜色（好、要留意、有问题）和最要紧的一句，点开看全部。

### 5.4 改进卡：让人知道怎么改进

- 地图顶上最多三张，按"值不值得"排：改什么、为什么（哪个健康信号）、多大（几分钟、几个文件）、风险。
- 例子：「旧灯箱没有功能在用，删掉，少 180 行」、「页面没有测试管作品弹窗，加 2 个」、「页面一个月大了 40%：作品的排序写在了页面里，挪回作品内容」。
- 点一张就是一个会话，范围是那一块。
- 不想做的点「不做」，同样的问题三个月内不再提。
- 来源：健康信号、交叉检查（第 3 节）、你点了才做的体检（第 7.6 节）。

### 5.5 地图怎么不烂

- **结构和健康每次由机器从代码算**，不靠 agent 记。
- **只有两样是人话**：块的名字和一句话职责。它们一过时就标出来。
- **不画到文件**：顶层 5 到 12 块，再往下一层，够用为止。

## 6. 决策

【已定】决策树是项目全局共享的，不是一个任务一棵。

### 6.1 什么算一个决定

- 有不止一条路，而且结果、代价或以后的维护明显不同。琐碎的不记。
- 四种来源，标在节点上：
  - **你定的**：你说的话，或你点的选项。
  - **替你定的**：agent 猜的，写明为什么、另一条路是什么。
  - **按规矩的**：照产品顶上一条和自带原则做的，默认折叠。
  - **它没说的**：机器查出来、agent 没报的（第 7.3 节），一律浮到最上面。
- 每个决定挂着：为哪张卡、碰了哪些模块、依赖哪些更早的决定、一个快照。

### 6.2 怎么看

- **主线**：已接受的决定，从开题往下按时间排。
- **支线**：会话里还没接受的决定，从它开始的地方岔出去；放弃的支线画成虚线，留着可比较，接受时清掉。
- **影响**：点一个决定，依赖它的后续决定都亮起来，并写一句"改它会牵动 5 个决定，碰到页面、上线"。
- **筛选**：按模块、按功能卡，或者只看你定的和替你定的。

### 6.3 回到这里

- **还没接受的决定**：「回到这里，换一条路」。先告诉你要重做几步、大约多久；代码退回快照，从那里重做；原来那条留着。
- **已经接受的决定**：「改这个决定」开一个新任务，开始前列出它牵动的决定和模块（就是第 6.2 节亮起来的那些）。
- 参考 IBIS、QOC、ADR："问题、选项、标准"的记法；它们难坚持是因为要人边干边记，这里由 agent 顺手产出。

### 6.4 并行任务

【已定】多个任务同时改很多东西时，要顾到冲突。

- 每个会话一个 worktree，代码上互不踩；冲突按模块和决定算。
- 开始时，要碰的模块另一个会话正在改，会话列表里那一行标一句「和 A 都碰页面」。
- 一个会话被接受后，其他碰到同一模块、或依赖了被改掉的决定的会话，在决策树上它们的支线标「需要重新对齐」：把它的决定在新基础上重放，报告哪几条不再成立，你点了才重做。
- 只在碰的模块不重叠时建议同时开（参考 Kiro 按依赖分批）。

## 7. 会话

### 7.1 范围：从哪里开始就是哪扇门

【已定】门的想法保留，但不用单独讲：

- 从功能卡「做这个」：范围是这张卡要碰的模块（Zirma 先猜，显示出来）。
- 从模块「从这里查」「改进它」：范围是这一块。
- 在预览里点一个区块：范围是那一块。
- 直接在会话里说：Zirma 猜一个范围，显示在输入框旁边，点一下能改。

要动范围外的模块、或者新加一块，就是一个决定，停下来问。

### 7.2 进度行

- 一步一行，写在做什么，原地更新；点开是命令和输出。【已定】
- 碰到底线、出范围时，这一行变成琥珀色并停下，下面出决定卡；不依赖这个答案的步骤接着做。

### 7.3 底线：不能不择手段

【已定】

- 来源：产品里的"不用什么"，加自带原则（可删的默认值）：
  - 先用项目里已有的语言、依赖、写法。
  - 新依赖、新运行时、新工具（Python、Docker、全局安装的包）都要作为决定提出来，附上不加的方案。
  - 只改范围里的模块；顺手看到的问题变成改进卡，不顺手改。
  - 不为了让测试过而改测试、跳过测试、关掉检查。
- 每一轮结束，主节点确定性地查：
  - 依赖清单和锁文件。
  - 新语言或新运行时的标志（JS 项目里出现 `requirements.txt`、`.py`、`Dockerfile`）。
  - shell 里的 `pip`、`brew`、`npm -g`、`curl … | sh`。
  - 删掉或跳过的测试，新加的 `@ts-ignore`、关检查的注释。
  - 范围外的模块。
  - 比例：你说了一句小事，它改了几百行。
- 做之前知道的：停下来出决定卡，引用来源（「产品里你写过不加 Python」）。做完才查出来的：决策树上补一个「它没说的」节点，浮到回执最上面。

### 7.4 回执

- **效果**：前后截图、预览链接、命令的真实输出。排第一。
- **决定**：这次在树上的那一段，默认展开"替你定的"和"它没说的"，每个都有「回到这里」。
- **底线**：一行一项。
- **变了什么**：产品里哪张卡变了状态、地图上哪块变了（新加、变大、健康变了）。各一句，点了过去。
- **没验证**：一行。

没事的时候整张卡一行：「作品区 6 → 9 张 · 测试过了 · 没有要你看的」。代码放在最底层。

### 7.5 接受和回退

- **接受** = 合并进你的分支，只有人能点。卡变"做好"，支线并进主线，没选的支线清掉。
- **整个退回** = 删掉分支和 worktree。
- **接受后反悔** = 第 6.3 节的「改这个决定」。

### 7.6 审查分层

1. **机器**：测试、类型检查、构建、底线检查、健康。
2. **独立审查**：改动超过一定大小（【待定】5 个文件或 150 行）时，一个上下文干净的模型只看结果，判断是不是最简单的做法、有没有沿用项目原来的写法；修不了的变成决定。小改动不跑。
3. **体检**：你点了才做，或每接受十来个会话提议一次。查重复、越来越乱的地方；结果进地图的改进卡。

## 8. 注意力和成本

**平时只有会话**：进度行、偶尔一张决定卡、一行回执。产品、地图、决策是你想看才去的地方。

| 东西 | 注意力 | 现实开销 |
|---|---|---|
| 进度行、回执 | 省注意力；没事一行 | 很小 |
| 产品 | 想功能时；空格只在卡上等你 | 卡的增删改是 agent 的工具调用，很小 |
| 地图 | 出问题或有改进卡时 | 结构和健康是确定的计算，秒级；一句话说明只在新块和过时时让模型写 |
| 改进卡 | 最多三张，不催 | 交叉检查免费；体检是一次较大的调用，你点了才做 |
| 决策 | 觉得不对劲时 | 快照是提交，很便宜；回去要重做，花多久先告诉你 |
| 底线检查 | 没事不出现 | 毫秒级 |
| 独立审查 | 一句话 | 每个大会话多一次模型调用 |

**可持续靠三条**：能算的都让机器算（地图结构、健康、底线、交叉检查）；agent 顺手产出的（决定、卡的状态、一句话说明）不要人记；要人维护的只剩名字和确认。

## 9. 不做

- **diff 当主界面**。代码在最底层，想看能看。
- **单独的开题流程**（v0.2）：开题就是第一版产品。
- **带缩略图的产品地图**（v0.2）：地方变成产品页的列；截图只在回执里。
- **临时生成、不保存的架构图**（v0.2）：变成常驻的地图，因为要长期跟住才有用。
- **四扇门的讲法**（v0.2）：变成"从哪里开始就是哪个范围"。
- **单独的并行页面**（v0.2）：变成会话列表里的一句和决策树上的标记。
- **近况页、记忆页**（v0.1）。
- **决定记录写进项目文件**：【已定】先不动。
- **逐条"允许一次"当默认。**

## 10. 用户能自己建什么、改什么

（按 `ARCHITECTURE.md` 9.1）

- **产品**：顶上一条、地方、卡、空格的选项，全部能增删改。
- **地图**：块的名字、一句话职责、怎么分块（合并、拆开、改对应的路径）；改进卡能"不做"。
- **底线**：自带原则只是可删的默认值。
- **决策**：给决定改名，把"替你定的"确认成"你定的"。
- **独立审查的门槛**：多大才跑，或者关掉。
- 没有写死的项目、框架、路径；原型里的作品集网站只是样例。

## 12. 引擎和主节点要加的

- agent 的工具（开发会话才有）：
  - `step(intent)`：开始新的一步。
  - `decide(question, options[], chosen, by, card?, modules?, after?)`：记一个决定；`by` 是 `you | guess | rule`；`after` 是它依赖的更早的决定；主节点这时打快照。
  - `ask_decision(...)`：同上，但停下来等你选。
  - `note_unverified(text)`。
  - `plan_edit(ops)`：在产品页上加、改卡和空格（对话里只回一句）。
  - `describe_module(id, job, provides[])`：写或重写一块的一句话说明。
- 主节点：
  - 每轮结束跑底线检查；查到没报的，补 `by: unreported` 节点。
  - 按模块的路径判断范围、算地图结构（引用关系）和健康。
  - 交叉检查，生成改进卡（最多三张，记住"不做"）。
  - 回到某个决定：从快照开新分支，让 agent 从那里重做。
  - 接受时：卡的状态、支线并进主线；找出要重新对齐的会话。
- 产品、地图的分块和说明、决策树存在主节点上【待定】。

## 13. 检验

- 一个不太懂代码的人，能指出"从哪一步开始和我想的不一样"，并一次点击回到那里。
- 给一个 bug 的描述，能在地图上指出该从哪一块查，并且那块的健康或最近的决定里有线索。
- 用三个月：地图上没有"不知道它在干什么"的块；每张改进卡做或不做都有记录；没有"不知道为什么在这里"的依赖或运行时。
- 拿 Zirma 自己试：地图应该画得出 core、server、ui、desktop、各个模块，每块一句话说得清。
- 没事的会话，回执一行，接受只花几秒。

## 14. 搭建顺序

1. **C1 进度行、回执卡、底线检查**：建在现有的步骤和回执上。
2. **C2 决定和快照**：`decide`、`ask_decision`、每个决定一个快照、回执里的决定段、「回到这里」。
3. **C3 地图**：分块方案、引用关系、健康、一句话说明、「从这里查」、范围判断。
4. **C4 产品**：顶上一条、地方和卡、空格、`plan_edit`、开题、「做这个」。
5. **C5 决策树视图**：主线和支线、依赖和影响、「改这个决定」、重新对齐。
6. **C6 改进卡、交叉检查、独立审查、体检。**

每一刀单独一个分支、一个 PR。
