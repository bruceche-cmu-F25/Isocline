# 提醒：日程快到了、待办快截止了、要紧的信来了

> 状态：v0.2，**2026-11-26 已批准**，§8 按建议定（只有截止日的待办不单独提醒；日程提醒默认开）。
> v0.2 的改动：对着 `zirma` 最新的代码（05d9ed0）重新核实了一遍，补了四处 v0.1 没看到的：欢迎语会把所有没送出的通知一口吞掉（§3 第 4 条）；生成通知必须挂在一个事件上（§3 第 5 条）；「新信」改成按收到时间算，不用另记同步状态（§2）；邮件加快读信不用改模块契约（§4）。§8 写上了我的建议答案。
> 起因：你 2026-11-25 说手机上「该来的没来」。查下来，推送本身没坏：11 月 24、25 日早上 7:30 的结果都推到了 iPhone，Apple 也收下了。没来的是日程、待办、邮件的提醒，因为 Zirma 从来不做这三种提醒。
> 依据：`packages/core/src/attention.ts`（决定用的表）、`packages/server/src/attention.ts`（分派）、`packages/core/src/notices.ts`（通知和过期）、`packages/server/src/push.ts`（推送的措辞）、`modules/calendar/src/types.ts`、`modules/todo/src/types.ts`、`modules/mail/src/types.ts`、`packages/server/src/todo-sources.ts`；[attention.md](attention.md)、[today-and-inbox.md](today-and-inbox.md)、[calendar-todos.md](calendar-todos.md)。
> 标记：**【事实】** 读代码核实过；**【默认】** 我的默认，等你点头。

## 0. 结论

1. **主节点按时间生成「提醒」**：日程开始前、待办截止前、要紧的信到了。主节点一直开着，所以 Mac 合着盖、App 没开、手机锁着，提醒都照样会生成。
2. **提醒怎么送到你，走现有的注意力规则，不另起一套。** 你在用某个窗口，就在那个窗口说；在 Mac 前，由形象说；哪台设备前都不在，就推到手机。只多一条：提醒都推。
3. **提醒过时就作废。** 日程开始了、待办过了截止时间，还没送出去的提醒直接丢掉。它不进通知页，也不并进「欢迎回来」，那里只放 Zirma 自己等你的事。
4. **提醒什么、提前多久，都是你的设置，每样一个开关。** 默认值：有钟点的日程提前 10 分钟；有钟点的待办提前 1 小时；邮件默认不提醒，你加了发件人才提醒。
5. **第一版不调模型。** 哪封信算要紧，由你列的发件人和 Gmail 的「重要」标记决定，不让模型去猜。

## 1. 现在的样子【事实】

| | 现在 |
| --- | --- |
| 会产生通知的事 | 五种：任务的提问、提议、任务被打断、任务结果、对外改动的结果。另外还有「欢迎回来」（`core/runs.ts`、`proposals.ts`、`outbound.ts`、`presence.ts`） |
| 日程 | Google 日历每 5 分钟同步一次（`calendar` 模块 `sync.everyMs`）。不读 Google 自己的提醒设置；Zirma 不会在日程开始前说任何话 |
| 待办 | 有 `due`（截止日）、`at`（截止钟点，按主节点的时钟）、`plannedOn`（打算哪天做）。到点不会提醒。从日历变来的待办（`source.kind = "calendar"`）和那个日程是同一件事 |
| 邮件 | Gmail 每 30 分钟同步一次（`mail` 模块 `sync.everyMs`）。有 `important`（Gmail 的「重要」）、`starred`、`category`。新信来了不会提醒；早上 7:30 的早报会用模型标出「风险」「等你」 |
| 推给手机的 | 只推「要你的」和任务结果（`ATTENTION.pushes`）。通知产生 20 秒后没人接手就推；超过 10 分钟没送出去就不推了，等你回来 |
| 通知可以过期 | `createNotice` 带 `ttlMs`，到时候没送出去就作废。欢迎语用的就是这个 |
| 通知要挂在事件上 | `createNotice` 要一个 `eventSeq`：每条通知都对着一件记下来的事 |
| 欢迎语 | 你回来时，`tellInWelcome` 把**所有**还没送出去的通知（欢迎语自己除外）都算作「欢迎语说过了」，之后不再一条条说 |
| 通知页 | `shell/inbox.ts` 只列认识的几种（任务结果、被打断、对外改动、欢迎语），认不出的种类不进来 |
| 窗口和形象说的话 | `noticeLines`（`ui/noticeText.ts`）认不出的种类，一律按「任务结果」说。Mac 的系统通知也用它 |
| 让一个模块马上读一次 | 主节点的 `passes.sync(id)`：不用等它自己的周期 |

## 2. 提醒什么、什么时候【默认】

| 来源 | 提醒哪些 | 什么时候 | 不提醒的 |
| --- | --- | --- | --- |
| 日程 | 有钟点的日程，你没拒绝的（自己建的、接受了的、还没回复的邀请） | 开始前 **10 分钟** | 全天日程；你拒绝了的；放假日（`isDayOff`） |
| 待办 | 有 `at`（截止钟点）、还没做完的 | 截止前 **1 小时** | 只有截止日、没有钟点的（早报已经列了「今天截止」）；从日历变来的（日程那边已经提醒）；已归档的 |
| 邮件 | 你列的发件人寄来的新信；另有一个开关：Gmail 标成「重要」、在主收件箱里的新信（默认关） | 同步时读到就提醒 | 你已经读过的；「重要的信」那个开关不管推广、社交、通知、论坛这几类（你点名的人，Gmail 归到哪类都提醒） |

- **「新」怎么算**：只提醒没读过、而且是在你打开这条邮件提醒之后、最近 1 小时内收到的信。不用另记「上次同步到哪」。第一次接上邮箱、或者刚打开提醒时，旧信都比这个时间早，所以不会一口气响一串。
- **一件事只提醒一次。** 每条提醒有自己的名字：日程是「日程 id + 开始时间」，待办是「待办 id + 截止时间」，邮件是邮件 id。同步了几遍、主节点重启了，都不会再响。日程改了时间、待办改了截止时间，名字就变了，所以会按新时间再提醒一次。
- **来得太晚的也提醒一次。** 日程是开始前 3 分钟才加的，同步到时离开始还有 1 分钟，就马上提醒。已经开始了就不提醒。
- **一次只说一件，太多就合并。** 同一分钟到期的几件，合成一条：「10 分钟后：组会，另有 1 件」。

**为什么不提醒「今天截止」但没钟点的待办：** 早上 7:30 的早报和「今天」页已经写了今天截止哪些。到中午再响一次，是第二遍。真要准点提醒，就给它一个钟点。

**和 Google 日历 App 重复：** 你手机上要是装了 Google 日历 App 并开着通知，日程会响两遍。所以日程提醒有自己的开关，见 §5。

## 3. 怎么送到你【默认】

提醒是第七种通知，种类叫 `reminder`。只改三处：

1. **类别**：`noticeClass` 把它算作「告诉你的」（`tells_you`），因为没有要你回答的事。
2. **推不推**：`ATTENTION.pushes` 加一条，提醒都推。
3. **作废**：提醒生成时带 `ttlMs`，到事情发生那一刻为止，也就是日程开始、待办截止的时候。邮件提醒的有效期是 1 小时。过了这个时间还没送出去，就当没发生过。
4. **欢迎语不吞提醒**：`tellInWelcome` 跳过 `reminder`。你回来时，没过期的提醒照常一条条送，过期的已经作废。不然你回到 Mac 前的那一刻，5 分钟后的会就被「欢迎回来」悄悄带过去了。
5. **记一件事**：每条提醒先记一个事件 `reminder.due`（主题是那个日程、待办或那封信），通知挂在它上面。这样「这件事是在哪告诉我的」查得到，和别的通知一样。

其余照注意力的表：

| 你在哪 | 提醒去哪 |
| --- | --- |
| 正在用某个窗口 | 那个窗口，用现有的「Zirma 说」小卡片，点它打开那个日程、待办或那封信 |
| 在 Mac 前，没看 Zirma | 形象跳一下说出来 |
| 哪台设备前都不在 | 推到手机，20 秒后 |

- **手机推送长什么样**（措辞放在 `push.ts` 的 `noticeMessage`）：
  - 日程：标题「10 分钟后：组会」，正文写地点，有视频会议就写「有视频会议」。
  - 待办：标题「1 小时后截止：交作业」，正文写它属于哪个领域。
  - 邮件：标题是发件人，正文是信的主题。
  - 点开：日程打开日历页，待办打开待办页，邮件打开那封信。点开就算看过了（`ack: true`）。直接打开那个日程或待办的卡片要等这两页能按链接打开一张卡，这一版不做。
- **不进通知页。** 通知页只放 Zirma 自己等你的事（today-and-inbox.md 的决定）。提醒说过就没了；它说的事本来就在日历、待办、邮件页上。
- **不并进欢迎语。** 你回来时，过期的提醒已经作废；没过期的照常送，不算「等你的事」。
- **网页锁开着时**（`hidePreviews`），手机锁屏上不显示内容，只有一句「打开 Zirma 查看更新」，和现在别的推送一样。

## 4. 放在哪【默认】

| 部分 | 放哪 | 为什么 |
| --- | --- | --- |
| 「现在该提醒什么」 | 一个纯函数，`packages/core/src/reminders.ts`：给它日程、待办、新信、设置和现在的时间，它返回该出的提醒 | 和注意力的表一样，规则只在一处，测试直接喂数据 |
| 定时和生成通知 | `packages/server/src/reminders.ts`，和 `todo-sources.ts` 一样，是唯一同时认识日历、待办、邮件三个模块的地方 | 模块之间不互相读表；从各自的快照拿数据 |
| 什么时候算一遍 | 每分钟算一遍；日历、待办、邮件一有变化就再算一遍 | 每分钟算一遍是对几十条日程和待办比一下时间，开销可以忽略 |
| 已经提醒过的 | 生成的通知本身就是记录：同名的提醒有了，就不再生成 | 不加新表 |

**邮件要更勤地读。** 现在每 30 分钟读一次，信来了最多要等半小时才知道。只要你开了任何一条邮件提醒，主节点的提醒那一块就每 5 分钟叫邮件模块读一次（`passes.sync("mail")`），开销和日历一样；邮件模块自己不用改。没开就照旧 30 分钟。

## 5. 设置【默认】

「设置 → 通用」里多一块「提醒」：

```
提醒
  日程      [开]   提前 [10 分钟 ▾]
  待办      [开]   提前 [1 小时 ▾]
  邮件      [关]   这些人来信时提醒： [+ 添加发件人]
                  [ ] Gmail 标为重要的信
```

- 提前多久，日程可以选 5、10、15、30 分钟或 1 小时；待办可以选 15 分钟、30 分钟、1、2 或 3 小时。
- 发件人是你的数据，默认是空的。也可以在邮件页的一封信上点「来信提醒我」，把这个人加进去。
- 设置存在主节点，所有设备跟着它。
- **以后可以加**：单独给某个日程、某条待办设提醒时间，放到卡片上。第一版不做。

## 6. 不做的

- **不读 Google 日历自己的提醒设置**（`reminders.overrides`），这一版统一按 §5 的提前时间提醒。
- **不让模型判断哪封信要紧。** 判断要调模型，花钱，还会出错。早报已经在用模型标「风险」「等你」，那个留在早报里。
- **不做「稍后再提醒」，也不重复提醒。** 一件事只响一次。
- **不补「刚离开时弹在 Mac 上、你其实没看见」的推送。** 这是注意力规则本身的缺口，另外处理。
- **不加勿扰时段。** 用手机的专注模式管。

## 8. 要你定的

1. **默认的提前时间**：日程 10 分钟、有钟点的待办 1 小时，可以吗？
2. **只有截止日、没有钟点的待办，不单独提醒**（§2），可以吗？还是要在当天某个钟点提醒一次，比如下午 5 点？
3. **日程提醒默认开着**，可以吗？你手机上的 Google 日历 App 开着通知的话，同一个日程会响两遍。
4. **邮件提醒默认关，只提醒你列的发件人**，可以吗？还是要默认打开「Gmail 标为重要的信」？
5. **开了邮件提醒就每 5 分钟读一次信**，可以吗？

我的建议（v0.2）：1 可以；2 不单独提醒，要准点就给它钟点；3 默认开，重复了你在设置里关掉一边；4 默认关，只提醒你列的人；5 可以。
